# Архитектурные решения

## 1. Слои и единый пайплайн

Конфигурация, доступ к БД, клиент модели, стадии пайплайна и способы запуска разнесены
по слоям. Стадии (`services/pipeline.py`) ничего не знают о способе запуска: HTTP, очередь
и Temporal вызывают один и тот же код. SQL живёт только в слое `repositories/`.

## 2. Миграции: SQL-файлы с собственным раннером вместо Alembic

**Решение.** Схема меняется файлами `db/migrations/NNNN_name.sql`. Раннер
`app/core/migrate.py` (`python -m app.core.migrate`) применяет их по порядку имён, каждый
в своей транзакции, и записывает версию в таблицу `schema_migrations`. Повторный запуск
ничего не применяет и сообщает, что новых миграций нет.

**Почему не Alembic.** Дальше схема будет состоять из pgvector-индексов, генерируемых
колонок и запросов с оконными функциями. Всё это пишется на SQL; ORM-прослойка и
автогенерация миграций только мешают: приходится писать сырой SQL внутри `op.execute`,
а автогенерация не знает про тип `vector`. Обычный SQL читается и ревьюится как есть.

**Цена.** Нет автоматических откатов (`downgrade`) и автогенерации по моделям.
Откат делается новой миграцией вперёд. Для проекта из пяти таблиц это приемлемо.

**Когда пересмотреть.** Если появятся несколько веток схемы или потребуется откат
в эксплуатации — перейти на Alembic, сохранив существующие файлы как начальную ревизию.

## 3. Эмбеддинги: multilingual-e5-base локально, косинус, HNSW

**Решение.** Векторы считает `intfloat/multilingual-e5-base` (278M параметров, 768
измерений) на процессоре через `sentence-transformers`; модель грузится один раз на процесс
(`lru_cache`), векторы считаются пачками по 32, нормализованные. Хранятся в `chunks.embedding
vector(768)`; метрика — косинус, индекс HNSW (`vector_cosine_ops`) построен под неё. Метрика
выбрана один раз: смена метрики требует пересборки индекса.

**Префиксы.** Модель обучена с `query: ` и `passage: `. Запрос и документ кодируются разными
вызовами (`embed_query`, `embed_documents`), префиксы лежат в настройках и взяты из карточки
модели. Без них близость релевантных пар проседает, и любой порог выметает верные результаты.

**Почему не LM Studio.** Модель считается внутри приложения: нет внешнего API, оплаты за
токены и зависимости от чужого сервера; `text-embedding-nomic-embed-text-v1.5` из LM Studio
ориентирована на английский. Цена: торч на процессоре (~250 МБ) и 1,1 ГБ весов один раз.

**Смена модели.** Другая размерность — новая миграция колонки; та же размерность — обнулить
`embedding` и запустить `python -m app.rag.reindex`.

## 4. Поиск: три режима и слияние RRF

- **vector** — ближайшие по косинусу, оценка = близость, ниже порога не отдаём.
- **keyword** — `plainto_tsquery('russian', …)` и `ts_rank_cd` по генерируемой колонке `tsv`
  (GIN). Все слова запроса должны быть в тексте: это «обычный» текстовый поиск, он не
  понимает перефразировок («мотор 800 Вт» не найдёт «Мощность: 800 Вт»), зато находит артикул
  буква в букву.
- **hybrid** — два списка по `search_candidates` (20) кандидатов сливаются по обратным
  позициям: `score = Σ 1 / (60 + позиция)` по спискам, где фрагмент встретился; запрос
  написан на SQL с оконной функцией `ROW_NUMBER()`. Фрагмент из обоих списков получает два
  вклада и оказывается выше. Порог действует на векторный список до слияния.

**Проверка на объёме.** На 363 фрагментах (выданные 5 документов + 100 однотипных из
`supplier-docs`) запрос по артикулу из спецификации (25 артикулов, верный фрагмент в топ-3):
по смыслу 22/25, по словам 25/25, гибрид 25/25. На пяти выданных документах (13 фрагментов)
поиск по смыслу находит артикул тоже — всё слишком близко друг к другу; промахи видны только
на объёме.

## 5. Порог релевантности: `search_min_score = 0.805`

Калибровка: `python -m evals.calibrate_threshold` (11 запросов с известным ответом, 6 «мимо»).
Косинусные близости e5 сжаты в узкий диапазон — мусор тоже получает 0.75–0.80:

| набор | верные запросы | запросы «мимо» |
|---|---|---|
| 5 выданных документов (13 фрагментов) | 0.783 … 0.869 | 0.753 … 0.791 |
| + 100 документов из `supplier-docs` (363 фрагмента) | 0.808 … 0.869* | 0.779 … 0.803 |

\* один верный запрос ушёл из топ-50 из-за 350 похожих фрагментов — это не вопрос порога.

Разделение узкое: лучший мусор 0.803, худший верный (без вытесненного) 0.808. Порог
**0.805** — середина зазора на большем наборе: ни один из шести мусорных запросов не проходит.
Цена — при пороге часть верных запросов на малом наборе (0.783–0.793) отсекается векторным
списком; в гибриде их возвращает словесный список. Шаг сказал: лучше вернуть меньше, чем
пустить мусор в контекст, — поэтому выбрана точность, а не полнота. Порог зависит от модели и
корпуса: после смены модели или заметного роста корпуса калибровку надо повторить.

## 6. Генерация по документам: три рубежа против выдумывания

`POST /generate {document_ids, hint}` → 202 и идентификатор; результат — `GET /jobs/{id}`.
Процесс `GenerateWorkflow` (Temporal) идёт по состояниям `queued → parsing → indexing →
retrieving → generating → verifying → awaiting_confirmation | needs_review → approved |
rejected | failed`; каждое пишется в базу отдельным шагом.

- **Контекст** (`rag/context.py`). Фрагменты подаются тегами
  `<source id="606" document="…" page="1" section="…">`; модель ссылается на `id` из базы,
  приложение его проверяет. Атрибуты экранируются (имя файла от постороннего не закроет тег).
  Предел — `context_max_chars` (6000), одинаковые тексты из разных документов берутся один раз.
- **Поиск.** Гибридный, внутри выбранных документов, запросы — подсказка (или имя файла) и
  аспекты («технические характеристики», «артикул модель», «гарантия комплект поставки»,
  «цена условия поставки»). Порог близости здесь 0: поиск ограничен документами, которые
  выбрал пользователь, и всё найденное в них — материал, а не мусор. Порог 0.805 из раздела 5
  остаётся для открытого поиска по всей базе.
- **Рубеж 2: проверка ссылок кодом** (`find_reference_issues`): фрагмент есть в базе **и** был
  в поданном контексте. Второе важнее: существующий, но не показанный модели фрагмент — это
  выдумка с правдоподобным видом. Плюс у каждой характеристики должна быть ссылка. Нарушение →
  переделка с текстом ошибки; при втором нарушении — `needs_review`, до проверяющей роли такая
  карточка не доходит. В результат попадают только верные ссылки, а документ, страница и секция
  берутся из базы, а не со слов модели.
- **Рубеж 3: проверяющая роль** сверяет значение каждой характеристики с текстом указанного
  источника; замечания — переделка (всего до трёх попыток).
- **Недостающие поля** определяет извлекатель по найденным источникам, а в карточку их
  добавляет код (`apply_facts_gaps`): значение, которого нет в документах, убирается, а
  уверенность ограничивается сверху. Ниже порога — `needs_review`, а не «готово».
- **Документы** разбирают их собственные процессы (`DocumentWorkflow`); генерация только ждёт
  готовности. Отвергнутый документ (скан) пропускается с пометкой, а если готовых нет — задача
  `failed` с причиной.

## 7. Стоимость, трассировка, метрики качества

**Учёт вызовов.** Таблица `llm_calls` (миграция 0005): задача, запрос, роль, модель, тариф,
токены на входе и выходе, стоимость, длительность, статус. Пишет клиент модели
(`llm/client.py`) после каждой попытки: расход берётся из ответа модели, задача и запрос — из
контекста логов, поэтому в новом месте учёт забыть нельзя — все вызовы идут через одну
границу. Сбой записи не роняет вызов. Деньги — `NUMERIC(14,6)` в базе и `Decimal` в коде,
округление до миллионной доли ₽ (`llm/cost.py`).

**Цены условные.** Модель локальная и бесплатная, поэтому в настройках стоят условные цены
(₽ за 1 млн токенов: основная 15/60, служебная 3/12), чтобы таблица и разбивка показывали
разницу тарифов. Это не деньги, а способ посчитать, сколько стоила бы та же работа.

**Две модели.** `LLM_MODEL` и `LLM_MODEL_LIGHT` (пусто — как основная). Политика в
`llm/policy.py`: служебные роли (`Critic`, `RagCritic`, `FieldFixer`, `Judge`) идут на
служебную модель и тариф `light`, извлечение и генерация — на основную. Сейчас обе настройки
указывают на `qwen3-14b`, различаются только тарифы; со второй, лёгкой моделью в LM Studio
достаточно поменять `LLM_MODEL_LIGHT`.

**Трассировка.** Идентификатор запроса рождается в `RequestContextMiddleware` (или берётся из
`X-Request-ID`) и возвращается заголовком; идентификатор задачи привязывается при создании.
Оба лежат в контексте логов (`structlog.contextvars`), идентификатор запроса — ещё и в
payload задачи. Воркер процессов (`temporal/tracing.py`) перед каждым шагом берёт
`job_id` из идентификатора процесса `card-<job_id>`, `request_id` — из payload и привязывает
их: записи шагов и вызовов модели несут оба id. Один `grep job_id=…` по логам показывает путь:
`job_created` → `http_request` → шаги процесса (`activity_started/finished` с длительностью)
→ `llm_call_done` (токены, стоимость, длительность).

**Запросы к учёту.** `make costs` — разбивка по моделям и тарифам; `make costs JOB=<id>` —
вызовы и стоимость одной задачи; `GET /jobs/{id}/cost` — стоимость задачи одним запросом.

**Метрики** (`make eval`, `make eval ALL=1`; код — `evals/`). Генерация по документам из
эталона (одна попытка, без переделок: измеряем сам генератор), три метрики:

1. *характеристики* — доля ожидаемых из `golden_cards.json`, совпавших с карточкой после
   нормализации значений («800 Вт» = «800 вт» = «800 Вт.», «1,5» = «1.5», «1 490» = «1490»);
2. *цитирование* — доля карточек, где каждая ссылка ведёт на фрагмент, который
   действительно содержит значение; страница берётся из базы по `chunk_id`;
3. *судья* — модель называет характеристики, которые источники не подтверждают, а долю
   считает код. Это оценка, а не истина.

Плюс полнота и точность списка недостающих полей. Отчёт сохраняется в `evals/reports/`
вместе с отпечатком промптов, чтобы сравнивать «до» и «после» правки.

Прогон на подмножестве (`blender_passport.pdf`, `kettle_manual.pdf`, `qwen3-14b`):

| документ | характеристики | цитирование | судья | недостающие P | ₽ |
|---|---|---|---|---|---|
| blender_passport.pdf | 1.00 | 1.00 | 1.00 | 1.00 | 0.21 |
| kettle_manual.pdf | 1.00 | **0.00** | 1.00 | 1.00 | 0.24 |
| среднее | 1.00 | **0.50** | 1.00 | 1.00 | |

**Самая слабая — цитирование (0.50).** У чайника 10 ссылок из 13 верны; три неверные — это
характеристики, которых нет в таблице документа, а модель вынесла их из прозы и пересказала
(«двойная стенка (металл снаружи, термостойкий пластик внутри)», «откидная с блокировкой»):
такого значения нет дословно ни в одном фрагменте. Метрика строже остальных по построению:
характеристики сверяются только с ключами эталона, поэтому лишние пересказы их не задевают, а
судья видит все фрагменты сразу и признаёт пересказ верным (1.00 на обоих документах — он
слишком мягок, к тому же судит та же модель). Метрика цитирования требует, чтобы значение
нашлось именно в указанном фрагменте и дословно, и сразу показывает то, что остальные
пропускают. Лечится промптом (значения только дословно, пересказы — в описание, а не в
характеристики) или более мягким сравнением значений; обе правки теперь можно измерить.
