# Архитектурные решения

## 1. Слои и единый пайплайн

Конфигурация, доступ к БД, клиент модели, стадии пайплайна и способы запуска разнесены
по слоям. Стадии (`services/pipeline.py`) ничего не знают о способе запуска: HTTP, очередь
и Temporal вызывают один и тот же код. SQL живёт только в слое `repositories/`.

## 2. Миграции: SQL-файлы с собственным раннером вместо Alembic

**Решение.** Схема меняется файлами `db/migrations/NNNN_name.sql`. Раннер
`app/core/migrate.py` (`python -m app.core.migrate`) применяет их по порядку имён, каждый
в своей транзакции, и записывает версию в таблицу `schema_migrations`. Повторный запуск
ничего не применяет и сообщает, что новых миграций нет.

**Почему не Alembic.** Дальше схема будет состоять из pgvector-индексов, генерируемых
колонок и запросов с оконными функциями. Всё это пишется на SQL; ORM-прослойка и
автогенерация миграций только мешают: приходится писать сырой SQL внутри `op.execute`,
а автогенерация не знает про тип `vector`. Обычный SQL читается и ревьюится как есть.

**Цена.** Нет автоматических откатов (`downgrade`) и автогенерации по моделям.
Откат делается новой миграцией вперёд. Для проекта из пяти таблиц это приемлемо.

**Когда пересмотреть.** Если появятся несколько веток схемы или потребуется откат
в эксплуатации — перейти на Alembic, сохранив существующие файлы как начальную ревизию.

## 3. Эмбеддинги: multilingual-e5-base локально, косинус, HNSW

**Решение.** Векторы считает `intfloat/multilingual-e5-base` (278M параметров, 768
измерений) на процессоре через `sentence-transformers`; модель грузится один раз на процесс
(`lru_cache`), векторы считаются пачками по 32, нормализованные. Хранятся в `chunks.embedding
vector(768)`; метрика — косинус, индекс HNSW (`vector_cosine_ops`) построен под неё. Метрика
выбрана один раз: смена метрики требует пересборки индекса.

**Префиксы.** Модель обучена с `query: ` и `passage: `. Запрос и документ кодируются разными
вызовами (`embed_query`, `embed_documents`), префиксы лежат в настройках и взяты из карточки
модели. Без них близость релевантных пар проседает, и любой порог выметает верные результаты.

**Почему не LM Studio.** Модель считается внутри приложения: нет внешнего API, оплаты за
токены и зависимости от чужого сервера; `text-embedding-nomic-embed-text-v1.5` из LM Studio
ориентирована на английский. Цена: торч на процессоре (~250 МБ) и 1,1 ГБ весов один раз.

**Смена модели.** Другая размерность — новая миграция колонки; та же размерность — обнулить
`embedding` и запустить `python -m app.rag.reindex`.

## 4. Поиск: три режима и слияние RRF

- **vector** — ближайшие по косинусу, оценка = близость, ниже порога не отдаём.
- **keyword** — `plainto_tsquery('russian', …)` и `ts_rank_cd` по генерируемой колонке `tsv`
  (GIN). Все слова запроса должны быть в тексте: это «обычный» текстовый поиск, он не
  понимает перефразировок («мотор 800 Вт» не найдёт «Мощность: 800 Вт»), зато находит артикул
  буква в букву.
- **hybrid** — два списка по `search_candidates` (20) кандидатов сливаются по обратным
  позициям: `score = Σ 1 / (60 + позиция)` по спискам, где фрагмент встретился; запрос
  написан на SQL с оконной функцией `ROW_NUMBER()`. Фрагмент из обоих списков получает два
  вклада и оказывается выше. Порог действует на векторный список до слияния.

**Проверка на объёме.** На 363 фрагментах (выданные 5 документов + 100 однотипных из
`supplier-docs`) запрос по артикулу из спецификации (25 артикулов, верный фрагмент в топ-3):
по смыслу 22/25, по словам 25/25, гибрид 25/25. На пяти выданных документах (13 фрагментов)
поиск по смыслу находит артикул тоже — всё слишком близко друг к другу; промахи видны только
на объёме.

## 5. Порог релевантности: `search_min_score = 0.805`

Калибровка: `python -m evals.calibrate_threshold` (11 запросов с известным ответом, 6 «мимо»).
Косинусные близости e5 сжаты в узкий диапазон — мусор тоже получает 0.75–0.80:

| набор | верные запросы | запросы «мимо» |
|---|---|---|
| 5 выданных документов (13 фрагментов) | 0.783 … 0.869 | 0.753 … 0.791 |
| + 100 документов из `supplier-docs` (363 фрагмента) | 0.808 … 0.869* | 0.779 … 0.803 |

\* один верный запрос ушёл из топ-50 из-за 350 похожих фрагментов — это не вопрос порога.

Разделение узкое: лучший мусор 0.803, худший верный (без вытесненного) 0.808. Порог
**0.805** — середина зазора на большем наборе: ни один из шести мусорных запросов не проходит.
Цена — при пороге часть верных запросов на малом наборе (0.783–0.793) отсекается векторным
списком; в гибриде их возвращает словесный список. Шаг сказал: лучше вернуть меньше, чем
пустить мусор в контекст, — поэтому выбрана точность, а не полнота. Порог зависит от модели и
корпуса: после смены модели или заметного роста корпуса калибровку надо повторить.
